# Conventions of the actions

The conventions every action of `scflow:core` follows. The catalogue of the
actions, with their parameters and example calls, is generated: see
[[scflow/actions]]; the concepts they work on are in [[scflow/concepts]].

- **Identifiers**: `scflow/<action_name>` (lowercase with underscores).
- **References by name**: A parameter that designates an entity takes the keyword `ref`, which the registry resolves before the body runs with `resolveReference` of the core ([References by name](../../core/docs/references.md)): an id, which is tried first, or the name of the entity as short as it stays unambiguous, `Line 1`, or `Lyon / Line 1` when two plants have a `Line 1`. The entities that are referred to by name, the type of their name and their scope are in [Names](spec/schemas.md#names); the other entities (flow, conversion, `item_at_actor`, `mode_stop`, `note`) are given by id. A reference that matches no entity, or several, is refused with `invalid_parameters`, and the error of an ambiguity lists the full qualified names of the candidates. The description of every reference parameter tells an assistant to give a name as short as it stays unambiguous, never an id it was not given, and that a localized name may be given in any language, but is written in the source language of the project. A result that returns an actor or a transformation gives its `reference`, qualified when the short name is shared, so that a caller can reuse it. The schemas referred to by name are listed in the generated topic `scflow/names`.
- **Atomic Transactions**: An action either succeeds completely or rolls back without leaving partial mutations in the model dataset. The action opens no transaction itself: the host runs it inside one.
- **Multilingual Support**: Localized text fields (the `name` of a type or of a scope, the `description`, the `schedule` of a mode) accept either a plain string or a localized map `Record<string, string>`; the `name` of an actor, an item, a mode, a transformation or a location is a plain string. An action receives no active language, so a plain string `s` is stored in the source language of the dataset, the first of its `languages`: `{ fr: s }` for `["fr", "en"]`, and `{ en: s }` when the dataset states none.
- **Parameter validation**: The registry checks `parameters` against their JSON Schema before the body runs and refuses a breach with `invalid_parameters`, so a body validates nothing by hand.
- **CRUD parameters**: An action that takes the place of a CRUD operation of a schema, named by the `crud` of that schema, follows the CRUD parameters of the meta-model (Action): a create takes the property names, an update takes `id` and the property names, and a delete takes `id` and `cascade`. A create takes every property of its schema, `tags` included.
- **Write limit**: Each action declares the schemas it writes in `writes`; a write outside them is refused with `write_not_declared`.
- **Read actions**: An action that only queries declares `kind: "read"`. The host runs it outside any undo transaction, so it writes nothing. The other actions are mutations (`kind: "action"`, the default).

### Rules

The [network rules](spec/implementation.md#network-rules) are declared on the schemas. The engine checks them at the end of the transaction of an action, and a breach refuses the whole action with `rule_violation`, whose details give `rule`, `schema` and `key`. A change of any instance that a rule reads is covered: changing the type of an actor or of an item is refused when an item it holds or carries no longer fits. A rule only refuses, so the actions still write what a rule requires, such as the holdings of the two ends of a flow. The rule `mode_serves_flow` compares the positions of the stops of a mode, which a declared rule cannot: the actions that can break it check it and throw an error that names it, which rolls the action back as a `rule_violation` does.

### Deletion and cascade

Every delete action, `scflow/remove_note` and `scflow/release_held_item` included, takes `id` and `cascade` (boolean, default `false`). `scflow/delete_flow` and `scflow/remove_note` accept `cascade` for consistency and it changes nothing. With `cascade: true`, `scflow/release_held_item` deletes the transformation lines that use the record. Without `cascade`, the action throws an error that counts the dependents and deletes nothing. With it, the action deletes the dependents first, in dependency order (transformation lines, conversions, held items, transformations, flows, actors from the deepest child to the root, items), then the target, so the engine never meets a restricted reference.

The notes of an entity are owned by it: deleting an entity deletes its notes, whatever `cascade` says, and a delete action never lists them as dependents. A deletion therefore removes the notes of the target and of every dependent it deletes.
