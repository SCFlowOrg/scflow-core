# Upgrading a model

A `schema` or `scalar_type` is created, updated or deleted by `runCommand` and
`runScript` like any instance, but only against an **upgrade locator**: a temporary
dataset that starts as a copy of the model and records the changes.

```ts
createUpgradeLocator(locator): Promise<string>
queryUpgradeLocator(upgradeLocator): Promise<{ source_locator: string; namespace: string; commandResult: CommandResult }>
checkUpgrade(locator, upgradeLocator): Promise<{ autoUpdate: TransientValue[]; modifiedSchema: TransientValue[]; lostSchema: TransientValue[] }>
upgradeDataset(locator, upgradeLocator): Promise<CommandResult>
```

1. `createUpgradeLocator(locator)` returns the upgrade locator.
2. Run schema and scalar type commands against it, as in the opening example of
   [mcl.md](mcl.md).
3. `checkUpgrade` lists the instances of `locator` that the change touches:
   updated automatically, schema modified, schema lost.
4. `upgradeDataset` applies the change, bumps the model minor version, deletes the
   upgrade locator and returns the impacted instances.

Rules:

- A schema command on a locator that is not an upgrade locator fails with
  `not_upgrade_locator`; a data command on an upgrade locator fails with
  `upgrade_locator`.
- The upgrade is **compatible**, and runs automatically, when it cannot invalidate a
  stored value: a scalar property added with a default, a property removed, a
  constraint relaxed or changed while every stored value still passes. It is
  incompatible when a mandatory relation is added, or a property changes type or
  array-ness. Setting `is_set` on an array is compatible only for the instances
  whose stored value holds no duplicate; their stored order is not rewritten.
  Setting `is_unique` follows the same rule.
- `upgradeDataset` of an incompatible change fails with `incompatible_upgrade` and
  changes nothing. The host may migrate the data itself, then bump
  `model_major_version`.
- Adding an extension schema (see [authoring.md](authoring.md), Extensions) is
  compatible: `upgradeDataset` creates, for each stored instance of the schema it
  extends and of the schemas extending that one, its extension instance from the
  defaults, and bumps `data_minor_version`. The properties an extension adds are
  not stored on the extended instances, so they are never backfilled there.
- Adding a facet to a module (see [modules.md](modules.md), Facets) writes
  nothing: the instance of a facet is created on its first value. A schema the
  dataset defines itself belongs to no module, so `facet_of` fails there with
  `constraint_violation`.
- A scalar type is created and never updated or deleted.
- The schemas of one `create` command may reference each other through
  `inverse_name`, in any order, and a schema may reference itself. A target found
  neither in the command nor in the model fails with `unknown_extends_target`.
- An `update` of a schema carries its complete authored description; whatever it
  leaves out takes the default. The inverse properties that other schemas generated
  on it are kept, including those generated by another entry of the same command.
- `queryUpgradeLocator` returns the recorded changes and the dataset they are for.

## How an upgrade locator works

- An upgrade locator is an ordinary dataset, created through the format's
  `createDataset`. It holds a copy of the model (the `schema` and `scalar_type`
  instances) and two internal instances that record the locator it is for and the
  state of the model when it was created. Whether a locator is an upgrade locator
  is therefore read from its own storage, with no in-memory registry, and holds
  across process restarts for every format.
- `upgradeDataset` deletes the upgrade locator once the upgrade succeeds: it is
  scratch for one round trip.
- A scalar property addition is always compatible, because every scalar type
  resolves some default. A property whose scalar constraints changed (`enum`,
  `pattern`, bounds) is compatible only for the instances whose current value
  still validates against the new definition.
- The `CommandResult` of `queryUpgradeLocator` is not index-parallel between
  `before` and `after`: a batch of model edits mixes additions, modifications and
  removals. A schema that was not edited but extends one that was is "considered
  as deleted" and appears in `cascade-deleted`.

## Modules

The protocol above changes the schemas and scalar types a dataset holds itself.
The schemas of the [modules](datasets.md#modules-of-a-dataset) of a dataset are
not changed by schema commands: a module is replaced by another version.

- A local module, `local:<name>`, is replaced with `setLocalModule`, which checks
  the stored instances as a compatible upgrade does and refuses an incompatible
  change with `incompatible_upgrade`.
- A published module is carried to a newer version with
  `upgradeModule(locator, manifest, { migrations })`. The migrations of the new
  manifest past the embedded version run in version order: a declared form
  rewrites the stored values under the embedded schemas, then the instances are
  checked against the new schemas as a compatible upgrade, the module is
  embedded at its new version, and each `body` runs through commands under the new
  schemas. `migrations` maps the version a body reaches to its code, which the
  bundle of the module gives. Every declared rule is checked last.

  ```yaml
  migrations:
    - to: 2.0.0
      rename_schema: { from: site, to: place }
    - to: 2.0.0
      rename_property: { schema: place, from: label, to: title }
    - to: 2.0.0
      delete_property: { schema: place, property: legacy }
  ```

  The upgrade is one step: any failure undoes it. An instance the new schemas
  cannot take, a schema that leaves the module with instances no migration moves,
  fails with `incompatible_upgrade`; an older version, a migration without exactly
  one form or a body with no code, with `constraint_violation`; a breach of a rule,
  with `rule_violation` listing every instance at fault in `details.violations`.
  Deciding when to upgrade (on open, versions and digests) is the host's.
- `upgradeDataset` also checks every declared rule once the new model applies,
  and refuses the upgrade with `rule_violation` when one breaks (see
  [rules.md](rules.md)).
- `refreshImport` fails with `import_not_upgraded` while the imported dataset
  uses another version of a module than the dataset (see
  [datasets.md](datasets.md#imports)).
